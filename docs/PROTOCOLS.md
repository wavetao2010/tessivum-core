# Protocols

Tessivum Core has two independent, exact-version wire contracts:

| Contract | Current accepted version | Boundary |
| --- | --- | --- |
| WASM plugin ABI | `cordis.plugin/v1` | Extism host ↔ guest |
| Legacy Node bridge | `cordis.node/v1` | Rust bridge ↔ Bun compat-host |

A service contract is versioned separately as `service-name@contract-version`.
Neither wire version substitutes for a service contract version.

## `cordis.plugin/v1` (Extism/WASM)

### Manifest

A package is a JSON manifest plus its relative WebAssembly entry point. The
host uses `WasmPackage::from_manifest_file` to read the manifest and the
`entry` file, or `WasmPackage::from_bytes` when both inputs are already in
memory. Unknown manifest fields are rejected.

```json
{
  "id": "example.echo",
  "version": "0.1.0",
  "entry": "example_echo.wasm",
  "abi": "cordis.plugin/v1",
  "inject": [],
  "permissions": ["cordis.log"],
  "configSchema": {
    "type": "object",
    "properties": {
      "enabled": { "type": "boolean" }
    },
    "required": ["enabled"],
    "additionalProperties": false
  },
  "exports": [
    "cordis_init",
    "cordis_call",
    "cordis_event",
    "cordis_update",
    "cordis_stop"
  ]
}
```

All fields shown are required. `id`, `version`, and `entry` must be nonblank;
`version` must be a three-component numeric semantic version; `abi` must equal
`cordis.plugin/v1`; and `inject`, `permissions`, and `exports` cannot contain
duplicates. The manifest and the actual WASM module must contain all five
exports. ABI or manifest validation occurs before an Extism guest instance is
created.

`configSchema` is a deliberately small JSON Schema subset. It recognizes
`type` (`null`, `boolean`, `integer`, `number`, `string`, `array`, `object`),
`properties`, `required`, boolean `additionalProperties`, `items`, and `enum`.
The validator does not claim support for other JSON Schema keywords.

### Lifecycle exports and envelopes

Every lifecycle export receives UTF-8 JSON encoded as:

```json
{
  "requestId": "example.echo:0",
  "context": { "entryId": "echo", "entryName": null, "inject": [] },
  "payload": {}
}
```

`requestId` is generated by the host for each instance (`<manifest id>:<sequence>`).
`context` and `payload` are JSON values. Loader activation calls `cordis_init`
with the entry configuration as `payload`; direct callers use `call`, `event`,
and `update` with their supplied values. `update` first validates the candidate
configuration and commits it only after the guest succeeds. `stop` rejects new
calls, requests cancellation of the active call, invokes `cordis_stop`, and
invalidates host bindings even if `cordis_stop` returns an error.

The host requires a response envelope with a matching `requestId`. Its current
deserializer accepts additional response fields, but portable guests must use
one of these documented PDK forms:

```json
{ "requestId": "example.echo:0", "result": { "ok": true } }
```

```json
{
  "requestId": "example.echo:0",
  "error": {
    "code": "METHOD_REJECTED",
    "message": "method is disabled",
    "phase": "call",
    "details": { "method": "echo" }
  }
}
```

The response `requestId` must match the request. If `error` is present, the
host returns it; otherwise `result` is required. Guests should send one of the
two forms above, even though the current Rust response deserializer ignores
unknown fields. Consumers must branch on `code` and `phase`, not `message` or
`details`. The host rejects an oversized input/output, malformed JSON,
mismatched request ID, or a response without `result` and `error` with a
structured `PluginError`.

`tessivum-pdk::export_guest!` implements the two documented forms for Rust
guests. It does not emit an `ok` discriminator.

### Capability functions

Capabilities are Extism functions in module `extism:host/user`. The manifest
can request only these v1 names:

| Function | PDK request payload |
| --- | --- |
| `cordis.log` | `{ "level": "trace\|debug\|info\|warn\|error", "message": "..." }` |
| `cordis.config.get` | `{ "key": "..." }` |
| `cordis.service.call` | `{ "service": "...", "method": "...", "payload": <JSON> }` |
| `cordis.event.emit` | `{ "topic": "...", "payload": <JSON> }` |
| `cordis.event.subscribe` | `{ "topic": "..." }` |
| `cordis.registration.dispose` | `{ "id": "..." }` |
| `cordis.kv.get` | `{ "key": "..." }` |
| `cordis.kv.set` | `{ "key": "...", "value": <JSON> }` |

A host-capability result is `{ "result": <JSON> }`; a capability failure is
`{ "error": <PluginError> }`. The PDK decodes `config_get` and `kv_get` JSON
`null` as `None`, decodes `event_subscribe` as `{ "id": "..." }`, and passes
all other success values to the caller's requested serde type. Capability
payload semantics and authorization policy remain host-defined.

Authorization is three-way: the guest must declare the permission, the
registry must grant it, and a handler must be registered. Otherwise the call
fails with `PERMISSION_DENIED` or `CAPABILITY_UNAVAILABLE` rather than falling
back to a default implementation.

### Instance resource contract

`ResourceLimits` is validated before instantiation. V1 requires nonzero
memory pages, timeout, fuel, input bytes, and output bytes; it requires
`max_concurrency == 1`. Defaults are 1,024 64-KiB memory pages, 5 seconds,
10,000,000 fuel, one concurrent call, and 1,048,576 input/output bytes. The
Extism engine applies the memory, timeout, fuel, and no-WASI/no-network-host
configuration. Calls are serialized per instance.

## `cordis.node/v1` (Legacy Node bridge)

### Frame encoding

Every frame is four bytes of unsigned big-endian body length followed by a
UTF-8 JSON object:

```json
{
  "protocolVersion": "cordis.node/v1",
  "connectionGeneration": 7,
  "kind": "plugin.load",
  "requestId": 42,
  "payload": {}
}
```

`connectionGeneration` is a nonzero unsigned 64-bit integer. `requestId`, when
present, is a nonzero unsigned 64-bit integer. The TypeScript decoder extracts
these root integers before ordinary JSON numeric conversion so it does not lose
u64 precision. The only permitted top-level fields are the five shown above;
`payload` is required.

The default maximum JSON frame body is 1,048,576 bytes. Both endpoints reject
an oversized declared length before allocating its body, reject empty frames,
require valid UTF-8 and JSON, and reject an invalid version, generation, or
request-ID placement. A `FrameCodec` can set another positive u32 limit; the
compat-host reads `CORDIS_NODE_MAX_FRAME_BYTES` for its limit.

### Kinds and request IDs

| Kind | `requestId` | Meaning |
| --- | --- | --- |
| `hello`, `ready` | absent | Startup handshake. |
| `heartbeat`, `log` | absent | Liveness or out-of-band diagnostic payload. |
| `response`, `error`, `cancel` | required | Settlement of an existing request. |
| `exit` | required | Request graceful host shutdown. |
| `plugin.load`, `plugin.update`, `plugin.dispose`, `plugin.snapshot` | required | Plugin lifecycle and inspection. |
| `service.call`, `service.provide`, `service.remove` | required | Generic service operations. |
| `event.subscribe`, `event.emit`, `event.callback` | required | Generic event operations. |
| `registration.dispose` | required | Remove a registered service or listener. |

`response` carries the successful JSON payload. `error` carries
`{ "code": string, "message": string, "details"?: <JSON> }`. `cancel` is
terminal for the request ID; the Rust client also includes
`{ "requestId": <id> }` in its cancel payload for compatibility with the host.

### Handshake, generation, and cancellation

The Rust client starts in `Handshaking`, sends `hello`, and does not admit any
request until `ready`. The Node host accepts only `hello` while new, records
its generation, initializes vendored Cordis, and replies `ready` with
`{ "protocolVersion": "cordis.node/v1", "maxFrameBytes": <number>,
"vendoredCordis": true }`. Subsequent frames must carry that same generation.
Version or generation mismatch, unexpected control frames, unknown kinds, and
invalid request IDs are fatal to that host connection; there is no v1 fallback
or partial compatibility mode.

The Rust client has bounded inbound and outbound queues. A full queue returns
`BridgeError::QueueFull`; a request timeout or dropped `BridgeRequest` removes
its local pending entry and sends `cancel` if it won the settlement race. The
Node host gives each incoming operation an `AbortController`; a matching cancel
aborts it and returns `CANCELLED` if it has not already settled.

### Operation payloads

The bridge transports JSON values. The compat-host accepts these operation
shapes; fields shown as alternatives are accepted for direct callers, while
`LegacyNodeRuntime` uses the first form below.

| Kind | Required payload |
| --- | --- |
| `plugin.load` | `{ "pluginId": "...", "package": { "specifier": "...", "location": "..." }, "entry": <Core Entry> }` |
| `plugin.update` | `{ "pluginId": "...", "config": <JSON> }` |
| `plugin.dispose` | `{ "pluginId": "..." }` |
| `plugin.snapshot` | `{ "pluginId": "..." }` (or `{ "loader": true }`) |
| `service.call` | `{ "name" or "service": "...", "method"?: "...", "args"?: [] }` |
| `service.provide` | `{ "name" or "service": "...", "registrationId"?: "...", "value"?: <JSON> }` |
| `service.remove` | `{ "registrationId" or "id": "..." }`, or a service name from which the default registration ID is derived |
| `event.subscribe` | `{ "event" or "name": "...", "callbackId": "...", "registrationId"?: "...", "options"?: <object> }` |
| `event.emit` | `{ "event" or "name": "...", "mode"?: "emit\|parallel\|serial\|bail\|waterfall", "args"?: [], "next"?: <JSON>, "result"?: <JSON> }` |
| `event.callback` | `{ "callbackId": "...", "args"?: [] }` |
| `registration.dispose` | `{ "registrationId" or "id": "..." }` |

For `plugin.load`, an absolute, `file:`, or relative `package.location` is used
as an import target; otherwise the package specifier is imported. The host
selects `entry.options.export`, `entry.export`, or `export` when supplied, and
otherwise uses the module default or module object. This is a compatibility
transport, not a package trust mechanism.

### Shutdown and supervision

An `exit` request causes the host to abort active operations, settle plugin and
registration disposers, dispose its root Cordis fiber, respond `{ "drained":
true }`, then emit an `exit` frame. `NodeSupervisor` releases every local
cleanup registered for that generation on disconnect, crash, protocol failure,
shutdown, or drop. It attempts graceful exit for its configured deadline and
terminates the child only if it has not exited.
